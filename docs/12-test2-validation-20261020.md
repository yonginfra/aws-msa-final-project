# 주문·배포·복구 기능 실제 검증 기록

2026년 10월 20일 · 실제 검증 및 실습 환경 종료 기록

## 이번 작업의 결과

`test2`에 작성한 코드를 AWS에 구축하고, 실제 주문과 이메일 수신, 실패 복구, 비밀번호 교체, 배포와 롤백까지 확인했다. 확인 중 발견한 오류는 수정하고 다시 검사했다.

개선된 코드는 `main`으로 옮겼고, 이전 `main`은 `test2`에 보관했다. 배포 PR #1은 본인 승인과 필수 검사 통과 후 병합했다. 병합된 커밋 `f635592`로 Argo CD가 Synced·Healthy 상태에 도달했고, 실제 GitHub 배포 점검도 성공했다. PR #2는 AWS 인증 설정 수정이며, AWS 적용은 끝났지만 코드 병합은 팀원 승인을 기다리고 있다.

## 기능이 연결되는 흐름

**주문 저장 → Outbox → SNS → SQS → Lambda → SES → 고객 이메일**

Outbox는 주문과 함께 ‘보내야 할 알림’을 DB에 기록한다. 발송 과정이 일시적으로 실패해도 다시 처리할 근거를 남긴다. SQS는 전달받은 알림을 보관하고, Lambda가 메시지를 읽어 SES로 이메일을 보낸다. 중복 이벤트는 DynamoDB 기록으로 걸러낸다.

**Secrets Manager → External Secrets Operator → Kubernetes Secret → 앱 DB 연결**

RDS가 관리하는 DB 비밀번호를 Secrets Manager에 보관하고, External Secrets Operator가 Kubernetes Secret에 반영한다. 이번 실습에서는 실제 비밀번호 변경 후 앱을 순서대로 재시작해 새 비밀번호로 연결되는지 확인했다. 비밀번호 변경과 동시에 앱 연결이 자동으로 모두 전환되는 구성이라고 설명하면 안 된다.

## PR 승인 후 배포 흐름

1. 앱 변경을 검사하고 변경된 서비스 이미지를 빌드한다.
2. CI가 이미지 digest 변경을 담은 배포 PR을 만든다.
3. 사람이 변경 내용을 승인하고 필수 검사를 통과하면 병합한다.
4. Argo CD가 `main`의 선언을 반영한다.
5. 배포 점검 작업이 Git 커밋·이미지·Pod 가용성·HTTPS·상품 API를 확인한다.

`main`에는 필수 검사, 승인 1명, 관리자에게도 적용되는 보호 규칙을 설정했다. 봇이 만든 PR #1은 본인이 승인할 수 있었다. 본인 계정이 작성한 PR #2는 다른 팀원의 승인이 필요하다.

**남은 작업:** [PR #2](https://github.com/yonginfra/aws-msa-final-project/pull/2) 팀원 승인 및 병합. 이 수정은 AWS에는 적용되어 있다. 병합 전 `main` 코드로 인프라 apply를 실행하면 신뢰 설정을 이전 값으로 되돌릴 수 있으므로 먼저 PR을 반영해야 한다. 삭제 전 실행 검증을 마친 시점의 세 Terraform 영역 계획은 수정 코드 기준으로 `No changes`였다.

## 발표·보고서에 적절한 설명

“Terraform과 GitOps로 구축한 운영 환경에 주문 실패 복구와 비동기 고객 알림을 연결했다. 정상 동작뿐 아니라 재고 부족, 서비스 중단, 중복 요청, 메시지 처리 실패를 직접 발생시켜 복구 결과를 확인했다. 비밀값 교체와 승인 기반 배포, 호환되는 프런트엔드 버전의 롤백도 실습했다.”

## 설명할 때 지켜야 할 범위

- SES는 샌드박스 상태여서 인증된 주소로 이메일을 검증했다. 일반 고객 전체 발송은 별도 운영 승인과 설정이 필요하다.
- 중복 발송 억제는 검증했지만, 모든 장애 시점에서 정확히 한 번만 발송된다고 보장하지 않는다.
- 롤백 실습은 현재 DB·API와 호환되는 프런트엔드 이미지로 진행했다. 과거 DB 스키마까지 되돌리는 실습은 아니다.
- DB는 Single-AZ다. 전체 시스템이 고가용성으로 완성됐다고 표현하지 않는다.
- DB 비밀번호를 Secrets Manager로 옮겼으며 JWT 등 모든 비밀값을 이전한 것은 아니다.
- DB TLS 연결은 검증용 클라이언트에서 확인했다. 기존 Java 앱 JDBC의 `useSSL=false`는 후속 보완 대상이다.
- 테스트 주문과 테스트 고객은 검증 기록으로 남겼다. 임시 DB 점검 Pod는 정리했다.

## 실습 환경 종료와 잔여 자원 확인

검증을 마친 후 비용 관리를 위해 실행 환경을 삭제했다. 앱을 먼저 제거하고, EKS 내부 운영 도구를 삭제한 다음 AWS 인프라를 삭제했다. 삭제 계획에서 생성·변경은 없고 삭제 대상만 있는지 확인한 뒤 적용했다.

| 구분 | 종료 결과 |
| --- | --- |
| 앱·운영 도구 | Argo CD 앱과 Kubernetes 관리 자원 19개 삭제 |
| AWS 인프라 | Terraform 관리 자원 122개 삭제 |
| 컴퓨팅·네트워크 | 프로젝트 EKS·실행 EC2·ALB·NAT Gateway·EIP·VPC 잔여 없음 |
| 데이터·이미지 | RDS·프로젝트 EBS·수동 스냅샷·ECR·상품 이미지 버킷 잔여 없음 |
| 알림·로그 | SNS·SQS·Lambda·DynamoDB·프로젝트 CloudWatch 로그·알람·CloudTrail 잔여 없음 |
| 로컬 | 실행 중인 Docker 컨테이너 없음 |
| 보관 | Git 코드·검증 기록·S3 원격 state 버킷·Route 53 호스팅 영역 |

두 Terraform 실행 영역의 state에 관리 자원이 남아 있지 않은지 확인했다. 서울 리전과 프로젝트 이름·태그·VPC를 기준으로 별도 AWS 조회도 수행했다. 다른 프로젝트나 모든 리전의 자원이 없다고 보장하는 점검은 아니다.

원격 state 버킷과 Route 53 호스팅 영역은 재구축을 위해 보관했으므로 계정 전체 요금이 0원이라는 뜻은 아니다. 삭제된 홈페이지·Grafana·Argo CD 주소는 재구축 전까지 접속되지 않는다. 실행 환경이 없는 동안 GitHub 배포 점검 변수 `ENABLE_DEPLOY_CHECKS`는 `false`로 설정했다.

### 종료 중 발견한 점

ALB가 먼저 삭제된 후 인프라 destroy 계획에서 기존 ALB를 조회하려다 실패했다. 삭제 계획에 `enable_website_dns=false`, `enable_management_dns=false`를 전달해 불필요한 ALB 조회를 생략하고 삭제를 진행했다. ECR 이미지와 상품·CloudTrail 버킷의 객체도 프로젝트 소유임을 확인한 후 비워서 삭제 방지 설정에 걸리지 않게 했다. CloudTrail 중지 이후 지연 도착한 로그 객체도 추가로 정리했다. state 버킷의 객체는 비우지 않았다.

마지막 노드가 종료 훅에서 대기할 때는 노드그룹이 삭제 중이고 희망 노드 수가 0이며 앱이 이미 삭제됐는지 확인한 뒤 해당 인스턴스의 종료 진행을 허용했다. 임의의 다른 노드나 ASG를 종료하지 않았다.

### 다시 시작할 때

1. 최신 `main`과 PR #2 반영 여부를 확인한다. 이전 코드를 현재 state에 그대로 적용하지 않는다.
2. 같은 PowerShell 창에서 비밀값을 준비하고 AWS 인프라부터 생성한다. 최초에는 두 DNS 연결 옵션을 `false`로 둔다.
3. ECR이 비어 있으므로 `main`의 이미지 워크플로에서 전체 빌드를 실행한다. 삭제 전 digest는 이력이며, ECR에 이미지가 남아 있다는 뜻은 아니다.
4. 앱 자동 동기화를 끈 상태로 EKS 운영 도구를 구성하고 Secret·이미지 준비를 확인한 뒤 앱을 배포한다.
5. ALB가 생성된 다음 DNS를 연결하고 HTTPS·로그인·주문·이메일을 확인한다. SES·SNS는 새 인증 또는 구독 승인 여부를 확인한다.
6. 읽기 역할과 클러스터가 준비된 다음 배포 점검을 다시 활성화한다.
